# AI 주의사항

> [!danger] 모든 AI와 협업자 필독
> 이 문서는 Randint Strategy Record에 참여하는 ChatGPT, Claude, DeepSeek, GLM 및 그 밖의 AI와 인간 협업자가 따라야 할 공통 작업 규약이다. 모델이나 도구가 바뀌어도 이 규약은 유지한다.

## 1. 이 위키의 역할

이 Obsidian 볼트는 단순 메모장이 아니라 다음 역할을 동시에 수행한다.

- 게임의 현재 구현 상태를 설명하는 위키
- User와 인간 협업자를 위한 설계·의사결정 기록
- 여러 AI 사이의 장기 인수인계 자료
- 구현, 부분 구현, 미구현 항목을 추적하는 기준 문서
- Unity 프로젝트를 변경하기 전 영향을 파악하는 참조 자료

대화 내용은 사라질 수 있지만 위키는 남는다. 중요한 결정과 확인 결과를 대화에만 두지 말고 적절한 위키 문서에 반영한다.

## 2. 현재 권한 경계

> [!warning] Unity는 Read Only
> `Assets`를 포함한 Unity 프로젝트 내부는 **읽기 전용**이다. 코드, 씬, 프리팹, ScriptableObject, ProjectSettings 및 기타 Unity 파일을 생성·수정·삭제하지 않는다.

> [!warning] Wiki도 기본은 Read Only
> `wiki` 폴더 역시 기본적으로 읽기 전용이다. User가 현재 요청에서 위키 갱신을 명시적으로 요청한 경우에만 문서와 Canvas를 필요한 범위에서 수정한다. `.obsidian/workspace.json` 같은 자동 생성 설정은 명시적 요청이 없는 한 수정하지 않는다.

권한이 바뀌었다고 추정하지 않는다. User가 명시적으로 새로운 권한을 부여하기 전까지 위 경계를 유지한다.

### Unity 변경 요청을 받았을 때

1. 기존 Read Only 규칙과 충돌함을 먼저 알린다.
2. 정확히 어떤 파일과 기능을 변경할지 범위를 제시한다.
3. User가 Unity 쓰기 권한을 명시적으로 허용한 뒤에만 변경한다.
4. 허용 범위를 넘어선 정리, 리팩터링, 파일 이동은 별도 동의 없이 수행하지 않는다.

### Wiki 변경 요청을 받았을 때

1. 현재 요청이 위키 쓰기를 명시적으로 허용하는지 확인한다.
2. 실제 Unity 구현을 읽어 문서와 대조하되 Unity 파일은 수정하지 않는다.
3. 요청과 직접 관련된 문서·Canvas만 갱신한다.
4. 변경 후 링크, Canvas JSON, Git 차이를 검증한다.

## 3. 작업 전 필수 열람 순서

새 AI 또는 협업자는 최소한 다음 순서로 현황을 확인한다.

1. [[랜드인트 작전기록 대문]]
2. 이 문서 `AI 주의사항`
3. [[00 프로젝트/프로젝트 개요|프로젝트 개요]]
4. [[00 프로젝트/구현 현황|구현 현황]]
5. [[TODO LIST/TODO LIST|TODO LIST]]
6. 작업 대상과 직접 관련된 시스템 문서
7. [[로직트리/세부 로직트리.canvas|세부 로직트리 Canvas]]

위키 설명만 믿고 구현을 단정하지 않는다. 정확성이 필요한 경우 관련 Unity 코드, 씬, 프리팹, 데이터 Asset을 읽어 현재 상태와 일치하는지 확인한다.

## 4. 사실의 우선순위

정보가 충돌하면 아래 순서를 따른다.

1. User가 현재 대화에서 명시한 최신 결정
2. 실제 Unity 코드·씬·프리팹·ScriptableObject
3. 이 위키에 기록된 확정 설계와 상태
4. TODO, 아이디어, 과거 대화 요약
5. AI의 추론

AI의 추론은 사실처럼 기록하지 않는다. 확인하지 못한 내용에는 `추정`, `검토 필요`, `미확인` 중 하나를 표시한다.

## 5. 구현 상태 판정

모든 기능은 [[00 프로젝트/상태 표기 규칙|상태 표기 규칙]]을 사용한다.

> [!implemented] 🟢 구현
> 씬 또는 데이터에 연결되어 있고 실제 호출 경로와 결과 처리가 확인된 상태.

> [!partial] 🟡 부분 구현
> 데이터, UI, 클래스 또는 일부 흐름은 있으나 전체 플레이 결과까지 이어지지 않는 상태.

> [!unimplemented] 🔴 미구현
> 설계 또는 TODO만 존재하거나 실제 결과를 만드는 코드가 없는 상태.

파일이나 클래스가 존재한다는 이유만으로 🟢 구현으로 판정하지 않는다. **씬 연결 → 호출 경로 → 결과 처리**를 확인해야 한다.

상태가 바뀌면 다음 항목을 함께 확인한다.

- [[00 프로젝트/구현 현황|구현 현황]]
- [[TODO LIST/TODO LIST|TODO LIST]]
- 관련 시스템 문서
- 관련 캐릭터·스킬·데이터 문서
- [[로직트리/세부 로직트리.canvas|세부 로직트리 Canvas]]

## 6. 문서 작성 규칙

- 기본 작성 언어는 한국어다.
- 클래스명, 메서드명, Asset명은 실제 표기를 유지하고 백틱으로 감싼다.
- 문서 상단에는 가능한 경우 frontmatter를 사용한다.
- 날짜는 `YYYY-MM-DD` 형식으로 기록한다.
- Obsidian 내부 연결은 볼트 루트 기준 경로와 표시명을 함께 지정하는 위키 링크 형식을 우선한다.
- 동일 내용을 여러 문서에 복제하기보다 기준 문서를 만들고 링크한다.
- Mermaid와 Canvas는 복잡한 흐름을 이해하는 데 도움이 될 때 사용한다.
- 텍스트 파일은 UTF-8을 유지한다.
- 문서 이름을 변경하거나 이동하면 모든 내부 링크와 Canvas 파일 노드를 확인한다.

### 권장 frontmatter

```yaml
---
tags: [분류/태그]
status: active
implementation: implemented # implemented | partial | unimplemented
updated: YYYY-MM-DD
---
```

문서 자체에 단일 구현 상태를 부여하기 어렵다면 `implementation`을 생략하고 각 항목에 상태를 표시한다.

## 7. Obsidian 및 Canvas 주의사항

- `.canvas`는 유효한 JSON이어야 한다.
- 노드 ID와 엣지 ID는 중복되면 안 된다.
- 파일 노드의 경로는 볼트 루트 기준으로 기록한다.
- Canvas 색상은 초록 `4`, 노랑 `3`, 빨강 `1`을 상태 표시에 사용한다.
- Obsidian이 열린 동안 Canvas의 위치와 JSON 서식을 자동 변경할 수 있다. 수정 직전에 최신 파일을 다시 읽고, 사용자가 조정한 노드 위치를 보존한다.
- `.obsidian/workspace.json`은 Obsidian이 자동 갱신할 수 있으므로 직접 편집하지 않는 것을 원칙으로 한다.
- CSS 상태 표시는 `.obsidian/snippets/implementation-status.css`를 사용한다.

## 8. 기존 작업 보호

- 다른 협업자나 AI의 변경을 자신의 작업으로 간주하지 않는다.
- 관련 없는 파일을 정리하거나 되돌리지 않는다.
- 변경 전 현재 파일 내용과 Git 상태를 확인한다.
- 충돌이 있으면 더 최신의 사용자 작업을 우선 보존한다.
- 대규모 치환, 폴더 이동, 문서 삭제 전에는 대상과 영향을 확인한다.
- 사용자가 요청하지 않은 Git commit, push, branch 생성, 병합, reset을 수행하지 않는다.
- 삭제가 필요하면 복구 가능성과 삭제 대상을 먼저 명확히 한다.

## 9. 추측과 창작의 제한

- 게임 규칙, 공식, 수치, 캐릭터 설정을 임의로 확정하지 않는다.
- 명일방주 원작 정보와 이 팬게임의 자체 설정을 혼합하지 않는다.
- 웹이나 외부 자료를 사용했다면 프로젝트 내부 사실과 구분하고 출처를 남긴다.
- Unity Asset에 있는 값과 코드 기본값이 다르면 실제 직렬화된 Asset 값을 우선 기록한다.
- 이름이 비어 있거나 효과가 없는 데이터는 자연스럽게 보완하지 말고 `미입력` 또는 `미구현`으로 기록한다.
- 이 프로젝트에서 `특수 카드`, `T`, `JK`, `조커`는 같은 카드를 뜻한다. 서로 다른 카드로 분리해 해석하지 않는다.

## 10. 안전과 정보 보호

- 비밀번호, 토큰, API 키, 개인 경로의 민감 정보가 문서나 로그에 들어가지 않게 한다.
- 프로젝트 파일을 외부 서비스에 업로드하거나 공유하지 않는다.
- 외부 전송, 배포, 게시, 메시지 발송은 User의 명시적 요청 없이 수행하지 않는다.
- 출처를 알 수 없는 스크립트와 명령을 실행하지 않는다.
- 파괴적 명령과 광범위한 자동 수정은 피하고 정확한 대상을 먼저 확인한다.

## 11. 작업 완료 전 검증

AI는 작업을 완료했다고 보고하기 전에 아래 항목을 확인한다.

- [ ] 요청 범위 안에서만 변경했는가?
- [ ] Unity Read Only 규칙을 지켰는가?
- [ ] 새 문서의 내부 링크가 실제 파일로 연결되는가?
- [ ] Canvas JSON과 파일 노드 경로가 유효한가?
- [ ] 구현 상태 색상이 규칙과 일치하는가?
- [ ] 기존 사용자 변경을 덮어쓰지 않았는가?
- [ ] TODO와 구현 현황에 동기화가 필요한가?
- [ ] 확인한 사실과 추정을 구분했는가?
- [ ] 변경한 문서와 남은 위험을 User에게 간결하게 보고했는가?

## 12. 인수인계 작성 형식

작업이 중단되거나 다른 AI에게 넘겨질 때 다음 형식을 남긴다.

```markdown
## 인수인계

- 작업 목적:
- 확인한 Unity 파일:
- 변경한 Wiki 파일:
- 확정된 사실:
- 추정 또는 미확인 사항:
- 남은 TODO:
- 주의할 충돌·위험:
- 다음 권장 작업:
```

대화 상대가 다른 AI라고 해서 설명을 생략하지 않는다. 다음 작업자가 이전 대화 없이도 이어갈 수 있어야 한다.

## 13. 현재 프로젝트의 핵심 약속

1. Unity 프로젝트는 User의 별도 허가 전까지 읽기 전용이다.
2. Wiki는 공동 기억이자 기본 읽기 전용 자료이며, User의 명시적 갱신 요청이 있을 때만 변경한다.
3. 구현 여부는 존재가 아니라 실제 연결과 결과로 판단한다.
4. 🟢 구현, 🟡 부분 구현, 🔴 미구현 색상 체계를 유지한다.
5. User의 데이터와 기존 작업을 보호한다.
6. 모르는 내용은 꾸며내지 않고 미확인으로 남긴다.
7. 중요한 결정은 다음 AI가 찾을 수 있는 문서에 기록한다.

> [!quote] 최종 원칙
> 빠른 작업보다 재현 가능한 정확성과 안전한 인수인계를 우선한다.
